# slm_chitu_send / Network sending — установка, настройка, как это работает

Заменяет ChituManager в связке CHITUBOX → печать: файл, нарезанный в
CHITUBOX и отправленный через «Отправка по сети», улетает напрямую на
ScaleX LAN Manager.

## Установка

### Требования

- Windows (используются нативные Windows API — `QSharedMemory`-хук,
  `user32`/`kernel32` через ctypes; на другой ОС работать не будет).
- Python 3.10+ (проверено на 3.14). Любой установленный интерпретатор —
  через сам Python.org, через `py`/PyManager или Microsoft Store, не
  принципиально.
- CHITUBOX (Pro или обычный) — сам слайсер, уже настроенный на вашу ферму.
- Работающий ScaleX LAN Manager, доступный по сети с этой машины.

### Шаги

1. Скопировать папку `slm_chitu_send` куда угодно на диск (в этом
   README путь не важен — скрипт не привязан к своему расположению).

2. Поставить Python-зависимости:

   ```bash
   pip install PySide6 pycryptodome
   ```

   - `PySide6` — окно пикера: нативные Qt-виджеты (не браузер, не
     WebView2 — обычное Windows-окно, оформленное под ScaleX через QSS).
   - `pycryptodome` — расшифровка блока настроек CTB-файла для точного
     определения принтера, под который был нарезан файл (см. раздел про
     точный парсер ниже). Не критично: без него slm_chitu_send сам
     переключится на резервный текстовый поиск по файлу — работать
     продолжит, просто чуть менее надёжно на редких форматах файлов.

   `slm_chitu_send_autostart.vbs` запускает интерпретатор по **полному
   пути**, не голым `pythonw.exe` — на этой машине голый вызов резолвится
   сразу в ДВА разных установленных Python одновременно (подтверждено
   живьём 2026-09-25), и оба лезут создавать один и тот же
   QSharedMemory-сегмент — CHITUBOX в итоге подключается к тому, который
   выиграл гонку, а он не обязательно тот, что реально работает. Ставьте
   зависимости именно в тот интерпретатор, путь к которому прописан в
   `.vbs`.

3. Открыть [`slm_chitu_send.py`](slm_chitu_send.py) и поправить под свою ферму
   константы в начале файла (поиск по `SCALEX_HOST`):

   ```python
   SCALEX_HOST = "192.168.0.118"   # IP или хост вашего ScaleX LAN Manager
   SCALEX_PORT = 8082              # его порт
   ```

   Больше ничего вручную настраивать не нужно — список принтеров,
   рекомендованные параметры экспозиции и статус «подготовлен» slm_chitu_send
   всегда берёт живьём из `GET /api/printers` на этом хосте.

4. Первый запуск — из консоли, чтобы сразу видеть лог живьём:

   ```bash
   python slm_chitu_send.py
   ```

   Ожидаемый вывод (и то же самое в `C:\slm_chitu_send\data\slm_chitu_send.log`):

   ```
   === slm_chitu_send started PID=... ===
   === ScaleX: http://<ваш хост>:<порт> ===
   === slicer_file_watcher: watching ...\SlicerFile ===
   === CHITUBOX protocol listening on 127.0.0.1:<случайный порт> ===
   CreateFileMappingW(...) OK (alreadyExisted=no), wrote "<порт>"
   === shared memory created=yes ===
   ```

   Если вместо `shared memory created=yes` видно `NO` — CHITUBOX уже
   держит этот сегмент занятым (сам открыт и уже подключился к
   ChituManager, либо ChituManager уже был запущен раньше). Закрыть и
   CHITUBOX, и ChituManager, снова запустить slm_chitu_send, потом уже
   открывать CHITUBOX.

   slm_chitu_send сидит в трее (значок рядом с часами, может быть спрятан
   под «Показать скрытые значки») — двойной клик по нему открывает диалог
   «отправить файл вручную», не дожидаясь реального захвата из CHITUBOX;
   правый клик — то же самое плюс «Открыть лог» и «Выход».

5. Проверка: открыть CHITUBOX, нарезать что угодно, нажать «Отправка по
   сети». ChituManager запускаться не должен вообще — вместо него должно
   само собой открыться отдельное окно «Network sending» с выбором
   принтеров. Если открылся именно ChituManager — см. «Диагностика» ниже.

### Автозапуск (по желанию)

Чтобы slm_chitu_send поднимался сам при каждом входе в Windows, без
открытой консоли. В этой папке [`slm_chitu_send_autostart.vbs`](slm_chitu_send_autostart.vbs)
уже создан и настроен — если переносите slm_chitu_send на новую машину/в
новую папку, поправьте в нём путь (`WshShell.CurrentDirectory`) и
повторите шаг 2. С нуля (например, на новой машине) шаги такие:

1. Создать `slm_chitu_send_autostart.vbs` рядом с `slm_chitu_send.py`:

   ```vbs
   Set WshShell = CreateObject("WScript.Shell")
   WshShell.CurrentDirectory = "<путь до папки с slm_chitu_send.py>"
   WshShell.Run "pythonw.exe slm_chitu_send.py", 0, False
   ```

2. Положить ярлык на этот `.vbs`-файл в папку автозагрузки Windows:

   ```
   %APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\
   ```

   (Быстрее всего — набрать `shell:startup` в адресной строке
   проводника, она откроет эту папку напрямую.)

Готово — при следующем логине slm_chitu_send поднимется сам, тихо, в фоне
(`pythonw.exe`, без консольного окна, с иконкой в трее).

Чтобы отключить — удалить ярлык из папки Startup, сам `.vbs` можно не
трогать.

Чтобы перезапустить вручную после правок `slm_chitu_send.py` (например,
поменяли `SCALEX_HOST`): закрыть все процессы `python.exe`/`pythonw.exe`,
запустившие `slm_chitu_send.py` (через «Выход» в меню трея, либо диспетчер
задач), и запустить заново — двойным кликом по `slm_chitu_send_autostart.vbs`,
либо `python slm_chitu_send.py` из консоли, если нужно видеть лог живьём.
**Если открыты окна пикера с ещё не отправленными файлами** — перезапуск
их закроет, лучше сперва отправить/закрыть их самостоятельно.

### Диагностика

- **Пикер не открывается, ChituManager запускается как раньше** — значит
  CHITUBOX не увидел slm_chitu_send. Проверить: slm_chitu_send вообще запущен
  (лог показывает `shared memory created=yes`)? CHITUBOX был открыт уже
  после запуска slm_chitu_send (сегмент разделяемой памяти читается один раз
  при старте CHITUBOX)? Если сначала открыли CHITUBOX, а slm_chitu_send
  запустили позже — закрыть CHITUBOX и открыть заново.
- **CHITUBOX подключился, но новый файл не подхватывается** — сам
  TCP-приём в slm_chitu_send однопоточный и блокирующий: пока
  `handle_client()` обслуживает уже открытое CHITUBOX-соединение, любое
  второе подключение просто ждёт в очереди ОС и не обрабатывается вообще.
  В норме не мешает (CHITUBOX держит одно постоянное соединение), но если
  оно оборвалось не штатно (краш CHITUBOX, обрыв сети без закрытия
  сокета) — slm_chitu_send может перестать видеть новые подключения до
  своего перезапуска. Если это когда-нибудь станет реальной проблемой —
  первое, что стоит проверить в логе: `CLIENT CONNECTED` без парного
  `CLIENT DISCONNECTED` после него.
- **Окно пикера не выходит на передний план, сидит в панели задач** —
  `force_window_to_foreground()` сначала обнуляет системный
  foreground-lock-timeout, затем эмулирует нажатие Alt (`keybd_event`) —
  без этого Windows 10/11 всё равно отклоняет `SetForegroundWindow` от
  фонового процесса. Если лог показывает `SetForegroundWindow declined
  even after the Alt-keypress trick` — окно всё равно открывается, просто
  без автофокуса, ищите его на панели задач/в Alt-Tab.
- **Реальный принтер начал печать без включённой галочки «Запустить
  печать»** — не должно происходить (см. SESSION NOTES в самом
  `slm_chitu_send.py` про отказ от `bulk-uploads/from-draft`), но если
  увидите это — немедленно сообщите: это будет означать, что ScaleX
  сам поменял поведение своего API.

## Как это работает

### 1. CHITUBOX подключается к нам, а не к ChituManager

CHITUBOX узнаёт порт «менеджера» через именованный сегмент разделяемой
памяти Windows (`QSharedMemory` под капотом) с именем:

```
qipc_sharedmemory_ServerPort07a1a6dcfadd97d64f9f7f13063e6345d8b33ce8
```

slm_chitu_send создаёт этот сегмент сам (`CreateFileMappingW`/`MapViewOfFile`
через ctypes, см. `create_shared_memory()`) и пишет туда номер своего TCP
порта ASCII-строкой. CHITUBOX при клике «Отправка по сети» находит этот
порт и коннектится напрямую к slm_chitu_send — ChituManager.exe не
запускается вообще, ни разу.

### 2. Прямой триггер сохранения файла — без UI ChituManager

Сам CHITUBOX (не ChituManager) умеет обработать сообщение

```json
{"MsgType": "SaveFile", "FilePath": "<путь>"}
```

— это обрабатывает его собственная функция `ChituManager::saveSliceFile`
(найдено декомпиляцией `CHITUBOX Pro.exe` в Ghidra), которая либо
копирует уже нарезанный файл, либо реально режет модель, а потом пишет
результат по указанному пути. slm_chitu_send (`handle_client()`) ловит пинг
CHITUBOX `LoadWindow` с `"Visible": true` (шлётся при каждом клике
«Отправка по сети») и в ответ сразу просит `SaveFile` с путём во
временную папку `C:\slm_chitu_send\data\pending\`. Когда CHITUBOX присылает
подтверждение с `SavePath`, файл копируется в `C:\slm_chitu_send\received\`
и открывается окно выбора принтеров.

Резервный вариант на случай сбоя протокола — `slicer_file_watcher()`,
фоновый поток, который следит за папкой, куда ChituManager обычно
сохраняет нарезанные файлы (`%LOCALAPPDATA%\ChituManager\...\SlicerFile`),
и подхватывает файл оттуда, если он всё же появился таким путём.

### 3. Определение, под какой принтер нарезан файл

CTB-файл (формат «Chitubox CTB (Encrypted)», magic `0x12FD0107`) несёт
внутри зашифрованный блок настроек (AES-256-CBC, ключ/IV зашиты в сам
формат — это обфускация формата, не защита конкретного файла), а в нём —
поля `MachineNameOffset`/`MachineNameSize`, указывающие на открытый
ASCII-текст с именем целевой машины (`extract_ctb_machine_name()`).
slm_chitu_send читает его точно по этим полям (нужен `pycryptodome`); если
файл не подходит под эту структуру (другой формат/версия) — резервный
план: текстовый поиск копирайт-строки CHITUBOX, имя машины лежит прямо
перед ней. В окне пикера принтеры с несовпадающей моделью можно спрятать
галочкой «Подходит под файл» (включена по умолчанию, если машину вообще
удалось определить).

### 4. Пикер — нативное Qt-окно, оформленное под сам ScaleX

На каждый пойманный файл slm_chitu_send открывает обычное Windows-окно
(`PickerWindow`, PySide6/`QMainWindow`) — без браузера, без встроенного
движка, без HTTP-сервера внутри slm_chitu_send вообще. Прогресс отправки
идёт напрямую из фонового потока в GUI-поток через Qt-сигналы
(`Signal`/`Slot`, авто-thread-safe), без опроса и без ручной синхронизации
потоков. Оформление — не настоящий `styles.css` (его нельзя применить
напрямую к нативным виджетам), а QSS (`PICKER_QSS` в коде), вручную
списанный с реальных значений переменных ScaleX (`--bg`, `--accent`,
`--green` и т.д.) — если тема ScaleX когда-нибудь поменяется, эти
константы надо будет свести заново.

Приложение постоянно живёт в трее (`QSystemTrayIcon`, закрытие любого
окна пикера не завершает процесс) — из трея доступны «Отправить файл
вручную…» (открыть любой слайс-файл с диска, в обход CHITUBOX), «Открыть
лог» и «Выход».

Возможности окна:
- Переименование файла перед отправкой.
- Поиск принтера, чекбоксы «Показывать включённые» / «Скрывать занятые» /
  «Подходит под файл».
- Мультивыбор принтеров, «выбрать все видимые» / «снять всё».
- Список принтеров обновляется живьём (раз в 5с) пока окно открыто и
  отправка ещё не началась — статус «подготовлен», занят/свободен и т.д.
  не устаревают, пока вы выбираете, куда слать.
- На каждой карточке принтера — если у него в ScaleX заданы рекомендованные
  параметры экспозиции, точечная галочка «применить рекомендации»
  индивидуально для этого принтера (по умолчанию выключена).
- Бейдж «Принтер подготовлен» / «Не подтверждён» — то же самое, что
  показывает сам ScaleX (`operatorPrepared`), чисто информационно.
- Галочка «Запустить печать сразу после отправки» (по умолчанию выключена).
- Прогресс-бар отправки — свой, под каждой выбранной карточкой принтера
  (не общий на весь экран), с реальными фазами и процентом.
- Кнопка «Закрыть окно» появляется, когда отправка завершена (успешно
  или с ошибкой).

### 5. Состав CTB — автозаполнение склада из ChituHook

Склад в ScaleX («состав CTB», `PUT /api/warehouse/ctb-mappings`) хочет
список складских компонентов и их количеств для каждого файла — чтобы
после печати списывать материал автоматически. Собственная подсказка
ScaleX (`suggestedCtbCompositionArticles` в его `app.js`) угадывает только
ОДИН компонент подстрокой по имени самого `.ctb`-файла — бесполезно для
плиты с несколькими разными деталями.

`goo_hook.dll` (см. «Файлы в папке» ниже) перехватывает у CHITUBOX Pro
момент сохранения среза и пишет рядом с `.ctb` JSON-файл с оригинальными
именами всех моделей на плите (`FL_HookedSaveSlice` в `goo_hook.c`).
`slm_chitu_send.py` читает этот JSON (`read_chitu_hook_model_names`) и
сравнивает каждое имя со складскими компонентами (`code`/`name`) —
**точным** совпадением (без учёта регистра/пробелов), не подстрокой
(`match_composition_components`). Панель с результатом — под полем имени
файла в окне пикера, только если сайдкар-JSON вообще нашёлся; реально
сохраняется в ScaleX вместе с самой отправкой файла, без отдельной кнопки.

**Выбор артикула при совпадении по названию (2026-09-28).** На складе
бывает несколько компонентов с одним и тем же `name`, но разными
артикулами/`code` — у названия самого по себе нет однозначного целевого
артикула. Для таких моделей вместо автоматического (и по сути случайного)
выбора первого попавшегося компонента пикер показывает отдельную строку
с выпадающим списком всех подходящих артикулов — оператор выбирает
нужный сам, выбор читается в момент отправки. Однозначные совпадения
(имя есть только у одного компонента) по-прежнему уходят в ScaleX
автоматически, без участия оператора.

### 6. Отправка в ScaleX

Всегда по одному запросу на принтер, но **параллельно** (по потоку на
принтер, не дожидаясь друг друга) — через одиночные эндпоинты
`POST /api/printers/{id}/files` (быстрый путь, без изменений таймингов)
или `POST /api/ctb/patch-and-upload` (когда для принтера реально нужно
применить рекомендованную экспозицию — пересобирает временную копию
файла на сервере ScaleX, ~1 минута). Именно на этих эндпоинтах
подтверждённо работает `X-Start-Print`/`autoStart` — «поставить в очередь
без печати» либо «поставить и сразу напечатать», в зависимости от
галочки. Bulk/`from-draft` эндпоинты ScaleX **намеренно не используются**
(см. SESSION NOTES в `slm_chitu_send.py`) — они помечены как
«экспериментальные» в самом ответе ScaleX и однажды запустили печать на
живом принтере, даже не получив в запросе ни одного поля про автостарт.

## Файлы в папке

- `slm_chitu_send.py` — рабочий файл, всё описанное выше.
- `slm_chitu_send_autostart.vbs` — тихий запуск для автозагрузки (см.
  «Автозапуск» выше — создаётся один раз при установке).
- `data/` — рабочие данные (раньше жили отдельно в `C:\own_manager`,
  2026-09-25 слиты в сам проект): `pending/`, `received/`,
  `slm_chitu_send.log`.
- `goo_hook/` — исходник DLL-хука на CHITUBOX Pro (`goo_hook.c` +
  `qml_probe.cpp`), который `slm_chitu_send.py` сам инжектит в каждый
  новый процесс CHITUBOX Pro.exe (см. «Состав CTB» ниже) — свой
  `build.bat`, собранная `.dll` в git не попадает.

## Заброшенные подходы (чтобы не наступать на те же грабли)

1. **Полная замена ChituManager** (свой клон Angular-интерфейса ChituManager
   + подмена XHR/fetch под чужой логин). Дошли до реального обхода логина
   и рендеринга всей фермы из 48 принтеров, но финальный триггер —
   WebSocket-коннект карточки принтера — не срабатывал ни при каком
   воспроизведении, несмотря на точное соответствие декомпилированному
   коду. Брошено.
2. **Дать CHITUBOX открыть настоящий ChituManager и смотреть его окно
   через UI Automation** (pywinauto) — отклонено как избыточное решение.
3. **SSLKEYLOGFILE для расшифровки трафика ChituManager** — заблокировано
   средой выполнения.
4. **Пикер через `pywebview` (нативное окно на движке WebView2) +
   собственный локальный HTTP-сервер, страница переиспользует настоящий
   `styles.css` ScaleX по сети** — визуально выглядело отлично (страница
   действительно была частью того же приложения), но сам pywebview стал
   прямой причиной нескольких реальных зависаний в проде: `win.events.closed`
   вешал весь процесс намертво прямо на регистрации обработчика;
   `patchMode="full"` подвесил процесс один раз во время реальной
   отправки; файл 200-300МБ дважды крашил процесс без единой трассировки.
5. **Отдельное Edge/Chrome `--app`-окно вместо pywebview** (тот же
   локальный HTTP-сервер и `styles.css` по сети, но окно — отдельный
   OS-процесс браузера, не может утащить slm_chitu_send за собой при
   крэше) — реально работало стабильнее pywebview, но добавляло лишний
   процесс и полагалось на `FindWindowW` по заголовку окна для
   определения, когда его закрыли. Оставлено на будущее в ветке
   [`edge-app-picker`](../../tree/edge-app-picker) — не в `main`, но
   рабочее, если Qt-пикер ниже когда-нибудь придётся откатывать.
6. **QSS-тема пикера с плейсхолдер-цветами** (написана без сетевого
   доступа к ScaleX, до первого реального запуска на рабочей машине) —
   не баг архитектуры, а просто устаревший черновик; актуальные цвета
   сведены с живого `styles.css` ScaleX, см. `COLOR_*`/`PICKER_QSS` в
   `slm_chitu_send.py`.

Текущая схема (прямой TCP-триггер `SaveFile` + нативный Qt-пикер) обходит
все проблемы выше — ChituManager вообще не участвует, а значит и его
UI/логин/WebSocket не нужны, и в самом slm_chitu_send нет ни браузерного
движка, ни отдельного HTTP-сервера, которые могли бы утащить процесс за
собой при сбое.
